## 二、统计表格"真列布局" —— 已完成（2026-10-16 晚 ~ 10-17 凌晨）

**原先的问题**：统计是一整块等宽文本，**中英混排对不齐**。
根因：`pad()` **已经**是按显示宽度补齐的（中文按 2 格），
真正原因是 **`monospace` 字体不含中文字形 → 中文回退到比例字体 → 实际宽度不是拉丁字符的整两倍**。
结论：**算法修不了，必须换渲染方式** —— 已按此换掉。

**做法：**

1. `activity_main.xml`：`statsText`（单个等宽 TextView）→
   `<LinearLayout android:id="@+id/statsTable" android:orientation="vertical">`；
   另加 `statsEmptyText` 负责空统计提示（原来那句话是文本报表里的字符串）
2. `MainActivity.renderStats()` 动态生成：**表头行 + 每个应用一行 + 合计行**
   - 每列一个 TextView + `layout_weight`（`STATS_WEIGHTS`，8 列固定比例）→ **列对齐由布局保证，与字体无关**
   - 应用名左对齐、限一行、末尾省略号（长名字宁可截断也不能换行，否则行高不齐）；
     **数字一律右对齐**（表格里数字的惯例，位数不同也好比较）
   - 排序：有广告的优先 → 有广告数 → 成功 → 点击 → 名称
   - 合计行的**有广告/成功**口径仍是"所有应用求和"、不是"表里这几行"，否则和复制出来的报表对不上
   - **间距**（第一版列对齐做到了、但挤在一起，第二版专门修）：`STATS_CELL_PAD_DP=2`（每格左右留白）、
     `STATS_LINE_SPACING=1.15`、表头/合计行上下各 6dp（数据行 4dp）、`STATS_HEADER_SP=9` 比正文小一档。
     原因：表头 3 个汉字（"有广告/成功率"）**比数字宽**，列宽其实是被表头定死的；
     10sp 时表头正好占满 48dp 的列 → 真机上"启动有广告"糊成一个词。相关量级见下
3. **表头下、合计上各一条 1dp 分隔线**（`addStatsDivider`）。颜色必须显式给
   （`stats_divider`，深色由 `values-night/colors.xml` 覆盖）——
   `?attr/colorOutlineVariant` 在这个主题下解析成 **0**，那样画出来是一条看不见的线
4. `StatsReport.build()` **没动**（`StatsReportTest` 仍 11 项全绿）——
   「复制统计」还是原来的纯文本报表，而它的排序是**按点击降序**，
   与界面这张表的排序**故意不同**：界面要突出"有广告"的应用，报告是给人粘贴看的
5. **验证（数值核对，不是"看起来对了"）**：真机 `uiautomator dump` →
   11 行（表头 + 9 个应用 + 合计）逐列比 x 起点，**每列只有一个取值**：
   应用 98 / 启动 349 / 有广告 458 / 点击 568 / 成功 678 / 失败 788 / 误点 898 / 成功率 1008
   - 间距实测：数据行高 47px（10sp×1.15），**行间空隙 6.7dp → 9.3dp**；
     表头/合计与数据行之间 9dp → 13dp（含分隔线）
   - **有没有被截断要看像素，不能看 dump**：`uiautomator` 给的是**整个 View 的 bounds**，
     格子是 `weight` 撑满的，所以每行 x2 都一样（都是 349），拿它算文字宽度会得出"最长的名字 83.7dp"这种假结论。
     从截图逐行扫描字形（背景亮度阈值）才是真的：最长应用名"掌上无畏契约"实际 **52dp**，
     名字列 83.7dp，还剩 31dp；数字列最挤的表头"有广告/成功率"左边距 **4.3dp / 4.7dp**，
     其余表头 14~15dp —— 都没有截断
   - 深浅两套主题都看过（深色下分隔线是 `#40FFFFFF`）
   - 存证：`_tools/shots/spacing_before_after.png`（**改前/改后对照**）、`stats_final_table.png`（浅色最终版）、
     `spacing_dark.png`（深色）、`stats_final.xml`（dump）
   - 构建：**128 项单元测试全绿**（做这一版时是 120，后来又加了测试；列对齐那次用 `--rerun-tasks` 全量重跑验证过）

**⚠️ 上面这条"强制重绑方法"我后来纠正过** ✗：**不能**用 `settings delete secure enabled_accessibility_services` ——
它会把列表里**别人的服务一起删掉** ✗（实测连 ColorOS 自己的"智慧数据感知"都被删过一次，系统后来自己补回 ✓），
而且清空之后，我们自己的服务可能进入 **"列表里有、框架却不肯重新绑定"** 的状态 ✗
（2026-10-17 凌晨实测：摘除自己那一条 / 整体清空再写回 / 唤醒屏幕 / 等 6 秒 —— 4 种设置层方法全部拉不回来 ✗）。
**可靠的强制重绑只有一条**：**请用户在「设置 → 无障碍 → 广告跳过」里关掉再打开** ✓ —— 也就是应用自己提示的那句话 ✓ 实测有效 ✓（03:19:32 日志出现「服务已连接」✓）。<br>
**再记一个验证陷阱（同一天连踩两次 ✗）**：判断"服务在不在"**不能**用 `dumpsys accessibility` 的 `Bound services` 去 match 包名 ✗ ——
那里打印的是**标签**（`label=广告跳过`）✗；而且这个字段**会折行**，服务列表一长就跑到下一行 ✗ →
`grep 'Bound services'` 只拿到第一行，**会漏判成"没绑定"** ✗✗。<br>
**该用什么判** ✓：① 应用内日志里 `onServiceConnected` 打的那行「服务已连接」（服务端权威证据 ✓）；
② 界面状态卡（心跳 + 精确"是否连着"标志 ✓）。**两条能对上，才叫"确认它活着"** ✓。
| **那个系统弹窗存在时，读界面文字会失真**（2026-10-17 踩到的坑，先记下来免得下次又误判成 bug） | ColorOS 的「检测到…获取无障碍权限」弹窗盖在我方界面上时：`uiautomator dump` 里 `statusTitle` / `statusDetail` 会是**空**，而**截图里还能看到一段旧文字**（于是"标题=已停止、详情=正在工作"这种**任何一次渲染都产生不了**的组合会出现，看起来像渲染 bug）。弹窗关掉后同一次 dump 立刻恢复正常。我为此连查三轮、换了三种工具（dump / `read_image` / 自写像素采样），**三种给出一致性互相矛盾的结果** —— 所以这条要连"**弹窗存在时这些工具都不可信**"一起记 |

## 四、本项目用血换来的规矩（务必遵守）

1. **验证要在正确的层级**
   - "和别的卡片一样" → 核对**属性**（逐条列出）
   - 颜色/样式 → **像素采样**（给出 RGB 数字，如"偏差 0"）
   - 位置 → **节点 bounds 的数值**
   - 行为 → 单元测试 + 真机日志
   - ❌ 别用"看起来对了"
2. **文本替换必须用唯一锚点**
   10-16 那天两次被批量替换坑到：`ageMs = 300` 误伤 `ageMs = 3000/3001`；
   `</androidx.core.widget.NestedScrollView>` 在文件里出现**两次**导致布局结构错乱。
   **改完立刻做结构自检**（标签配平、字段计数）。
3. **先确认"我读到的就是这一次的结果"，再谈结论**（2026-10-17 修心跳时连栽三次）
   - 同一个 `/sdcard/x.png` 反复 `pull` 会拿到**哈希完全相同**的旧图；
     `uiautomator dump` 也会返回上一轮的内容 → 我把"看起来没变"当成"行为没变"，
     先后得出两个**错误结论**（"ColorOS 弹窗导致误报"、"停掉服务界面不报"）
   - 还 grep 过一行**已经从构建里删掉的**日志（`心跳核验`），找不到是必然的，却当成"没发生"
   - 可靠的是**带时间戳的来源**：`logcat`、`dumpsys`；要截图就先删本地旧文件、并确认哈希变了再看
   - 一句话：**"没有观测到"不等于"没有发生"，也可能是我看错了地方**
   - **主动证明"我这次拿到的是新的"**（2026-10-17 复核方补充，比上面更省事）：
     界面**自己带了一个会变的新鲜度标记** —— 状态卡片那行「**最后活跃 N 秒前**」每 5 秒就会变。
     于是：
     1. 先 `dump` 一次，记下 N；
     2. **等 6 秒以上**再 dump 一次（实测这个间隔**不够**，见下面写手方的复测；起步仍可这么试）；
     3. **两次的 N 必须不同** → 说明拿到的是新内容 ✓
                若两次完全相同 → 你读到的就是同一份旧内容 ✗（截图同理：两次哈希必须不同）

     ⚠️ **2026-10-17 实测修正（写手会话指出，复核方采纳）**：上面"**等 6 秒**"是**错的** ✗✗ ——
     `uiautomator dump` 的**陈旧窗口可达 5~16 秒**，6 秒不足以跨过它，会**假阴性**（把新内容判成旧内容）✗。
     正确做法：**以文件哈希为主判据** ✓，两次间隔拉到 **≥20 秒** ✓（哈希必须不同）；
     "最后活跃 N 秒前"这类会变的数字只作**辅助** ✓，不要单独拿它判新鲜度 ✗。
     教训：**连"验证手法"本身也要被验证** ✓ —— 这条手法是复核方凭"跑一次看起来成立"就写进文档的 ✗。

   - **`git check-ignore` 的坑**（2026-10-17）：传**绝对路径**会误报"未被忽略" ✗ →
     要用**相对路径 + `--no-index`** ✓。例：
     `git -C <repo> check-ignore --no-index -- "adskip-release.jks"` ✓
     （判断"密钥类文件有没有被忽略"时尤其别用错 ✗ —— 误报会让你以为它会被提交 ✓） ✗（截图同理：两次哈希必须不同）
        ⚠️ 但"N 相同"**不能直接判定陈旧** —— 原因见下面第 1 条补正

     这个办法的好处：**不依赖文件时间戳、不依赖哈希、也不依赖"我记得刚才是什么样"** ——
     界面自己就能证明自己是新的 ✓ 而且服务在"正在工作"和"已停止"两种状态下都会显示这一行 ✓
     对付"dump 拿到上一轮内容"这类错，比事后怀疑有效得多 ✓

     **已实测（2026-10-17 复核方）**：相隔 7 秒两次 dump，`最后活跃 1 秒前` → `最后活跃 4 秒前` ✓ 可用。

     **但写手方复测时发现两处要补的地方（2026-10-17，实测）**：

     1. **只看 N 会有假阴性**：心跳**上报**每 30 秒一次，而界面**刷新**每 5 秒一次，
        所以 `age` 在 0~4 秒之间会被 `describeAge` **一律显示成"0 秒前"** ——
        这段时间内两次 dump 的 N 相同，**但内容其实是新的** ✗。
        我复测时就撞上了（相隔 7 秒两次都是 `0 秒前`，连文件哈希都相同）。
        → **判据要以哈希为主、N 为辅**：哈希不同即可确信是新内容；
        N 相同**不足以**判定陈旧，要再等更久重测。
     2. **陈旧窗口比想象的长**：实测 `uiautomator dump` 会**连续约 5~16 秒返回哈希完全相同的内容**
        （有一次连拍 4 次、跨 16 秒，哈希一直是 `30EB404615`；另一次只卡了 5 秒）。
        所以"等 6 秒"不够，**建议等 20 秒以上**再判定；判成可疑就重测，代价只是多等一会儿。

     **合并后的可靠做法**：两次抓取间隔 **≥20 秒**，**文件哈希必须不同**（这是主判据）；
     再用 N 变化做辅助确认。两次都相同 → 当作没读到，重测 ✓

     **一个巧合要注意**：心跳每 30 秒一次，会把这一行重置，所以"两次数字恰好相同"**理论上可能偶然发生** ✗
     → 判成"可疑"就再等 10 秒重测一次 ✓（误判成"过期"只是多测一次，代价极小 ✓）
     → 更稳的做法是**同时比文件哈希**：两次 dump / 两次截图的哈希都必须不同 ✓
       （哈希只要有任何变化就会变，而且"读到旧文件"这种错必然表现为哈希完全相同 ✗）
4. **改动要能被证伪**
   给出"改完之后日志/数值应该变成什么样"的可检验预测，再让用户去看。
5. **宁可不动手**
   10-16 那天为同一个小改动连续引入 3 次回归（`nodeBounds`、节点键、盲点延迟）。
   **收益小、风险高的改动，不做。**
6. **别用"自己也会写的那本账"做判据**（2026-10-16 深夜，修计数不一致时踩的）
   第一版把广告门禁写成"比较 `lastAt` 里的时间戳"，看着天经地义，实际永远为真：
   `shouldRecord` 在**接受**时会顺手把 `lastAt[pkg]` 更新成 now，
   同一次观察里 `now - lastAt` 就恰好是 0，永远落在去抖窗口内
   （实测 5 次观察全判成"可以记广告"）。
   **教训**：判据要用"决策时**记下来的结论**"（一个布尔量），
   不要去反推一个**会被后续步骤改写**的状态。
   排查手法也记一下：把实际取值 `println` 出来、和"内联同一套算式"的结果对照，
   一眼就能分出是"我的算式错"还是"编译出来的东西和我想的不一样"。

## 六、服务心跳那次误报的修法（2026-10-17 凌晨）

**症状**：`dumpsys accessibility` 里 `Bound services` 一直在、心跳也一直在报（"最后活跃 27 秒前"），
界面却显示「⚠ 服务已停止」，而且每 5 秒弹一次 Toast。也就是**这个功能反过来在骗人**。

**根因**：`ServiceHeartbeat.connected` 这个内存标志**一旦被置假就恢复不了**，
而唯一把它置假的地方是 `AdSkipService.onUnbind()`。真机上 `onUnbind` 会在服务仍正常工作时被触发，
于是标志永久为假、界面永久报停止。

**改法（四处）**

1. `AdSkipService`：把"我不在了"从 `onUnbind` 挪到 `onDestroy`。
   `onDestroy` 才是"服务真被销毁"的可靠信号；`onServiceConnected` 每次重连都会走到，所以状态能自愈。
   心跳定时器也不再在 `onUnbind` 里停 —— 服务若还有实例在跑，让它继续报"我在"。
2. **心跳上报前先向系统核一次**（`AdSkipService.isStillEnabled()`，用 `AccessibilityManager.getEnabledAccessibilityServiceList()`）：
   核过了才 `beat()`，没核过就 `onServiceDisconnected()`。原来"定时器一到就报"只证明**进程和 Handler 还活着**，
   证明不了无障碍服务还连着 —— 核一次就把"实例没了但定时器还在跑"这条谎报路径堵住，
   而且**最迟一个心跳周期（30 秒）就能发现**，不用等 2 分钟的陈旧阈值。
   核验失败时只清"我在"标志、**保留** `lastAliveAt`，界面能同时显示"已停止 + 最后活跃 N 秒前"。
3. 判据抽成纯函数 `HeartbeatPolicy.classifyService(connected, ageMs, uptimeMs, graceMs)` →
   `RUNNING / STOPPED / CHECKING`，放在 `engine` 层所以能单测（补了 6 项）。
   规则是**两个条件都要满足**才算 RUNNING：标志为真 **且** 心跳新鲜。
   宁可偶发误报"已停止"，也不能在服务真没了的时候还显示"正在工作"（那正是这个功能最初要修的谎）。
4. **心跳状态机抽成 `engine/HeartbeatState`（纯逻辑），并且 `beat()` 会把"连着"置回真** ——
   这一步是**另一个会话补的，我原来没做到**：我那边 `beat()` 只更新时间戳，
   于是"存活核验**瞬时失败**"（抛异常、或系统正在重绑的空档）把标志清掉之后，
   界面会一直停在「⚠ 服务已停止」，**只能等系统下一次重绑才恢复** —— 而重绑频率是系统行为，
   不该成为正确性的前提。现在 `beat()` 成功一次就算自愈（`HeartbeatStateTest` 7 项钉住）。
   `util/ServiceHeartbeat` 退化成"给纯逻辑状态机接上 `SystemClock`"的薄封装

> **为什么不用"能读到 `rootInActiveWindow`"当存活依据**（另一个会话提过这个方向，我改了做法）：
> 读不到窗口是**已知的正常失败模式**（`AdSkipService.evaluateOnce` 里专门为它留了日志：
> "读不到界面内容（rootInActiveWindow 为空）…部分机型的开屏窗口读不到"）。
> 拿它当存活依据，会在那种时候把心跳判死 → 界面报"服务已停止"，
> 正好把这次修好的假警报又装回去。所以活着的依据取**系统说我们还挂在已启用列表里**，
> 那是 OS 的事实，不受"这个界面读不读得到"影响。

## 七、构建与真机验证的循环

```powershell
# 构建（项目内自带 Gradle / SDK，必须在项目内设置环境变量）
powershell -File build.ps1            # 不要加 task 参数（历史上踩过：参数绑定丢失导致装到旧包）

# 安装 + 重新绑定服务
adb install -r app\build\outputs\apk\debug\app-debug.apk
```
- **务必核对 APK 时间戳**，并可 `aapt2 dump` / 解包 `assets/rules.json` 确认内容 —— 曾被"旧 APK"骗过一次
- **重装之后不需要手动重绑**（2026-10-17 实测，见第五节的对照实验）：系统约 0.45 秒内自己绑回。
  重绑命令仍然有用，但它现在的适用场景是"**设置被清空**"那种（`am force-stop`、权限回收）：
  `adb shell settings put secure enabled_accessibility_services <包名/服务类名>`
- ⚠️ **`adb shell am force-stop <包名>` 才是把无障碍服务弄掉的那个操作** —— 它会把
  `enabled_accessibility_services` **清成 `null`**，而且**之后不会自动恢复**（设置已空，系统没有可绑的东西）。
  排查/验证时如果用过 force-stop，那之后看到的任何"服务不在"都是自己造成的，别记到重装头上
- **`settings put ... ""`（空值）会失败并报 `Bad arguments`** —— 想"停掉服务"做对照实验，
  要写一个不存在的组件名（如 `com.example.nonexistent/.Svc`），系统会把它规范化成 `null`
- **界面截图/`uiautomator dump` 可能是上一轮的结果**（同一路径反复 pull 会拿到哈希完全相同的旧文件）。
  判断行为是否真的变了，优先用带时间戳的 `logcat`；要截图就先删掉本地旧文件、并确认哈希变了再看
- `.ps1` 文件必须是 **UTF-8 with BOM**（PowerShell 5.1 会把无 BOM 的当 GBK 读）

## 九、2026-11-10 志愿汇与黑名单的四项改动（含证据与回退方案）

> 背景：距上次交接隔了 24 天，攒到 **志愿汇 41 启动 / 34 广告 / 128 点击 / 25 成功 / 74%** 的真机数据，
> 点击/广告 ≈ **3.8**（健康值应接近 1）。三项改动都由日志坐标逐条核对得出，不是拿来试的。

### 9.1 死节点黑名单：分级 TTL + 计数不再随时间清空（`737455a`）

- **旧实现的问题**：`blacklist()` 用同一个 `ttlMs` 既判"是否还拉黑"又删记录 → 两次使用间隔超过 30 分钟，**计数被一起清空**。
  志愿汇约 1.5 次/天启动，所以黑名单**从未生效**。设备上的持久化当时就是证据：`com.zzw.october:id/tvSkip@2,0 = count=2`（阈值是 3，永远到不了）。
- **新语义**：计数只由"成功"清除；拉黑时长分级 3~5 次 30 分钟 / 6~9 次 6 小时 / ≥10 次 24 小时；30 天没再失败才遗忘。
- **风险判断（写手提出、我方独立复核后同意）**：触发条件是"同一节点连续失败 10 次且中间无一次成功"（成功即清零），
  达到 10 次的节点对我们已属系统性失效；每天少跳一次广告的代价 < 旧实现每次启动白送 4 次点击、预算打光后完全不跳。

### 9.2 跨重启作废（`7303bba`）

时间戳用 `SystemClock.elapsedRealtime()` 且持久化，而它**重启后从 0 重数** → `now - lastFailAt` 恒为负 →
分级 TTL 与 30 天遗忘**全部失效**，黑名单实际持续"上次开机时长 + 分级 TTL"。
修法：清理条件加 `lastFailAt > now`（记录时间比现在还晚，只可能来自上一次开机）。回归测试：`重启后_上一轮开机的失败记录立即作废`。

    改为比较**注入手势之前**与 **1000ms 后**当场读出的窗口列表：
    * 只看**点击时存在、校验时消失**的目标应用窗口（窗口身份 = `id/type`）；
    * 广告若是独立窗口，它的根包名可能读不到、但类型是普通应用窗口，也算相关窗口；
      系统窗口（状态栏/输入法，type≥2）一律排除；
    * **只多出新窗口不算证据**（任何弹窗/新 Activity 都会让窗口出现）；
    * 窗口身份不比较包名可读性/焦点/层级/坐标 —— 这些都会抖。

  - **Activity 名与"包名变化"都不当成功判据**（真机抓到假成功）：0ms 盲点出手时，新一次启动的

    1 秒后事件到达变成 `LaunchActivity`，就被当成"Activity 切换 → 成功"记了一次假成功
    （2026-11-10 21:16 日志：`盲点校验 → 判定成功（Activity MainActivity → LaunchActivity）`，
    当时窗口列表其实**没有变化**）。另外判定入口本来就要求"根节点包名 == 目标包"才允许出手，
    所以能看到的包名变化只剩"读不到 → 读到"这种可读性变化，同样不能当广告关掉的证据。
  - **判定成功时仍跑落地页强特征兜底**：窗口被换掉也可能是"点到广告本体 → 同包新 Activity"，
    命中 `LandingPageDetector.STRONG` 时**不计成功也不计失败**（与文本路径同口径）。
  - **因果对照（关键，防止把应用自己推进当成点击成功）**：关掉无障碍服务、**不点任何东西**启动志愿汇，
