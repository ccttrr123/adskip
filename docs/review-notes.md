## 2. 两个分歧，以及各自怎么解决的

### 2.1 复核方提的方案被否（复核方认错）

复核方建议：把心跳存活依据从"定时器到点"改成"**确实能读到无障碍窗口**（`rootInActiveWindow`）"。

写手方**拒绝**，理由有代码依据：读不到窗口是**已知的正常失败模式** ——
`AdSkipService.evaluateOnce` 里专门为它留了日志（"读不到界面内容（rootInActiveWindow 为空）…
部分机型的开屏窗口就是读不到"）。拿它当存活依据，会在那种时候把心跳判死 →
界面报"服务已停止" → **正好把当时刚修好的假警报装回去**。

改用系统级核验：`AccessibilityManager.getEnabledAccessibilityServiceList()`
（`AdSkipService.isStillEnabled()`）——同样达成"证明得了自己还连着"，且不受"某个界面读不读得到"影响。

> **复核方确认：它是对的，我的建议是错的。** 记在这里，免得以后再提一遍。

### 2.2 写手方的实现有残留漏洞（写手认账）

复核方复核后指出：写手那版**只做了一半**：

```
isStillEnabled() 瞬时失败（抛异常 / 系统正在重绑的空档）
  → onServiceDisconnected()  → connected = false
  → 之后每次核验成功只调 beat()，而 beat() **不碰** connected
  → 界面判据是 connected && fresh  → 于是继续报「服务已停止」✗
  → 只能等系统下一次重绑（onServiceConnected）才自愈
     —— 而重绑频率是系统行为，不该成为正确性的前提 ✗
```

**复核方的修法**：收紧 heartbeat 语义 —— *调用方只有在通过存活核验之后才报心跳*，
所以 `beat()` 顺手把 `connected` 置真 → **每次核验成功都自愈（30 秒粒度）**，不依赖重绑频率。
为了让这条**能被测到**，把状态机抽成纯逻辑 `engine/HeartbeatState`，
`util/ServiceHeartbeat` 退化成"接 Android 时钟"的薄壳（**公开 API 未变 → 调用方零改动**）。

> **写手方确认：这条复核方的版本比我的强，已接受。**
> 我是"写的人"，在这一条上没看出自己的漏洞 —— 这正是分工的意义。

### 2.3 一处措辞：写手方说得过头了（写手认账）

写手方曾在协作状态里写"复核方不要再改 `AdSkipService.kt` / `ServiceHealth.kt` /
`HeartbeatPolicyTest.kt`"。事实是：复核方改的是**它自己新建的** `HeartbeatState.kt` /
`HeartbeatStateTest.kt` 和薄壳化的 `ServiceHeartbeat.kt`，**写手点名的那三个文件它一个都没动**。
而且复核方自己记录着它一度**特意不改**本文件（"如果它正在写，我就先不动"），
是用户明确说"可以追加"之后才写的。

**先守规矩的是复核方**，写手那条通知既没必要、也把话说重了。

> **教训**：协作通知写"**我在写哪些文件**"，不要写"**你不许动哪些文件**" ——
