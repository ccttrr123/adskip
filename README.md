# 广告跳过（adskip）

一个在 Android 上自动点掉其他 App 开屏广告"跳过"按钮的工具。**免 root**，基于无障碍服务。

> 当前状态：**已在真机上验证过 15 个应用**；135 项单元测试全绿；规则库 20 条。
>
> 已验证可用的应用（开屏广告能被点掉）：贴吧、微博、知乎、B站、京东、网易云音乐、
> 腾讯视频、掌上无畏契约、易校园、云运动、学习通、菜鸟、KOOK、米游社、爱奇艺；
> 志愿汇 约 80%（它屏上有个点不动的干扰节点，已用"跨启动黑名单"处理）。
>
> 还没做的：同包落地页识别（M2）、读不到跳过按钮时的端上兜底、F-Droid 上架。
> 开发过程中的踩坑、被否决的方案与两条会话的协作复核记录都在 `docs/` 里 —— 动代码前先读那份交接文档。

---

## 这个项目做什么、不做什么

**做**：在你打开某个 App 时，发现屏幕上出现了开屏广告的"跳过/关闭"按钮，替你点一下。
那个按钮本来就是监管部门要求必须提供的（[《互联网弹窗信息推送服务管理规定》](https://www.gov.cn/zhengce/zhengceku/2022-09/09/content_5709179.htm)），本工具只是替你完成这一次点击。

**不做**：
- 不修改其他 App，不注入代码，不 hook 任何进程
- 不破解、不代理、不中间人解密任何流量
- 不上传任何界面内容或使用数据
- 不接管银行、支付、政务类应用（这类应用检测到无障碍服务会拒绝运行）

## 已知不能解决的问题

- **摇一摇广告**：靠加速度计触发，应用层无法拦截，只能由系统提供开关（如 vivo OriginOS 5 的"仅开屏禁止"）
- **自绘且无规律的跳过按钮**：没有节点信息也没有固定位置时无法定位
- **同包落地页误判**：点到广告后如果落地页开在**同一个 App 内部**，M1 无法与"成功跳过"区分（见下文路线图）
- **Android 13+ 的"受限设置"**：侧载安装的 App 默认无法开启无障碍服务，需要用户手动放行或走一次 ADB

## 架构

设计上最重要的一条边界：**判定逻辑完全不含 Android 代码**。

```
AccessibilityEvent ──┐
                     ├─→ NodeReader ──→ UiSnapshot ──→ RuleEngine ──→ Decision
rootInActiveWindow ──┘   (Android 侧适配)   (纯数据)     (纯逻辑)      (纯数据)
                                                                            │
                                          AdSkipService ←───────────────────┘
                                                │
                                    注入手势 / ACTION_CLICK / 返回键
                                                │
                                          点击后校验 + 误点回退
```

这样切分的直接收益：项目里最容易出错、最需要反复验证的"判定准不准"，
可以在**没有真机、没有模拟器**的情况下用 JVM 单元测试覆盖。

| 文件 | 职责 |
|---|---|
| `engine/UiNode.kt`、`engine/UiSnapshot.kt` | 与 Android 无关的界面抽象 |
| `engine/RuleEngine.kt` | 全部安全规则的集中地 |
| `engine/SkipTextMatcher.kt` | "跳过"按钮的文本与倒计时识别 |
| `engine/LaunchTracker.kt` | 前台包名切换追踪，为时间窗提供依据 |
| `service/AdSkipService.kt` | 事件翻译、动作执行、点击后校验 |
| `service/NodeReader.kt` | 节点树 → `UiNode` |
| `service/GestureTapper.kt` | 手势注入（自绘按钮的唯一出路） |

## 六道安全阀

这个项目的风险不是"没跳过"，而是**点到广告本体**——那会让用户直接卸载。因此：

1. **时间窗**：只在该 App 进入前台后的 `windowMs` 内介入（默认 3 秒，解析时强制不超过 10 秒）
2. **熔断**：界面一旦出现输入框或"登录/注册"文案，立刻永久放弃本次启动
3. **点击上限**：每次启动最多注入 3 次点击
4. **盲点需旁证**：没有文本依据的坐标点击，必须先有倒计时 / 全屏媒体 / Activity 名命中作为旁证
5. **误点隔离**：连续误点 3 次后，本次运行不再介入该应用
6. **点击后上锁**：点击之后到校验结果回来之前，禁止对该应用再次判定

第 4 条是一处刻意的设计：`tap_ratio` 这种"盲点右上角"的策略如果不加旁证，
就等于每次启动都往右上角点一下，迟早出事。所以规则里必须显式声明
`evidence`，只有命中的旁证才能解锁盲点策略。

第 6 条是**真机实测逼出来的**。第一版没有这道锁，结果是 B站 上出现连点：
第一次点掉广告后，14ms 后第二次点击落在了广告底下的界面上，
而那个坐标正好是底部导航栏的「我的」，于是用户被带到了"我的"页面。
详见下方"真机迭代记录"。

### 候选筛选：为什么用"倒计时证据"而不是"位置"

只取"遍历到的第一个文本命中节点"会点到错误的东西。真机数据（1216x2640）：

| 节点 | 位置 | 有倒计时/控件 id 证据 | 结论 |
|---|---|---|---|
| B站「跳过 5」`#count_down` | 84%,**92%** | 有 | ✅ **真按钮**（在最底部） |
| 贴吧「跳过 05」 | 85%,4.6% | 有 | ✅ 真按钮 |
| 微博「跳过」 | 88%,10.3% | 无（但在顶部边缘） | ✅ 真按钮 |
| 贴吧「广告跳过」 | 84%,74.4% | 无 | ⛔ 内容区，不是按钮 |
| B站「广告跳过」 | 25%,46.7% | 无 | ⛔ 广告可点区域正中 |

**这里有一个我犯过并纠正的错误，值得记下来：**

第一版我只看位置，发现"所有正确点击都在顶部"，就设成**只认屏幕顶部 25%**。
结果真机日志打脸了：

```
「跳过 5」TextView#count_down@(888,2363,1160,2499)[可点]
```

B站 的跳过按钮 view id 就叫 `count_down`，中心在 92% 高度处 —— **它的跳过按钮真的在最底部**。
"禁止底部"的思路直接把它误杀了。**不同 App 的跳过按钮位置本来就不同，位置不能当主要判据。**

所以现在的策略是：

1. **有强证据（倒计时文案，或 view id 含 `count_down`/`countdown`/`skip`）→ 任意位置都接受**
2. **没有强证据 → 只接受屏幕边缘**（顶部 25% 或底部 20%）。中间是内容区，那里出现"跳过"文案基本都不是按钮，点它等于点广告
3. 无条件否决**面积超过屏幕 40%** 的候选 —— 广告 SDK 常给整块广告容器挂上含"跳过"的描述，点它的中心就是点广告本身

规则里保留 `"skipRegion": "top"` 这个收紧开关，给"底部存在危险元素"的个别 App 用；
默认是 `"full"`，因为位置限制会误杀真按钮。

> 注意第 1 条里"倒计时"必须要求**秒数大于 0**：
> `countdownSeconds("跳过")` 返回 0（表示"是跳过文案但没有倒计时"），
> 如果只判断 `!= null`，光秃秃的「跳过」就会被当成有倒计时证据，整个策略会被架空。
> 这个 bug 正是被单元测试抓出来的。


### 真机迭代记录

| 轮次 | 发现的问题 | 修复 |
|---|---|---|
| 第 1 轮（OPPO Reno 15 / ColorOS 16） | B站 连点导致跳到「我的」页面 | 加入点击后上锁 + 900ms 全局冷却 + 成功后 10 秒冷却 |
| 同上 | 贴吧 先点到 (1022,1965) 的「广告跳过」，1.8 秒后才点到正确的 (1037,122) | 候选排序（`SkipTargetRanker`） |
| 同上 | 「已达点击上限(3)」在每个事件上重复打印 | Wait / Abort 加时间冷却去重 |
| 同上 | 日志只有坐标，无法判断匹配到的到底是什么节点 | 日志带上类名、view id、可点性；被否决的候选也会打印 |
| 第 2 轮 | 同一句日志每 4 秒重复一次：我用"包名变化 = 新启动"清状态，而系统弹窗/输入法也会让包名来回切换 | 状态全部改成基于时间，与包名切换语义解耦 |
| 第 2 轮 | "打开应用完全没有日志"无法排查 | 把 `Ignore` 拆出 `Expired`（超出时间窗），并补上"读不到界面内容"的日志 |
| 第 2 轮 | **我自己的误判**：只看位置设成"只认顶部"，误杀了 B站 位于 92% 高度的真按钮 | 主判据改为"倒计时/控件 id 证据"，位置只在没有证据时作为边缘判定 |
| 第 2 轮 | 单元测试发现 `countdownSeconds("跳过") == 0` 被判成了"有倒计时证据" | 要求秒数大于 0，否则策略被架空 |
| 第 3 轮 | **"跳过得有点慢"**：只在无障碍事件到达时判定，而开屏广告多是静态图几乎不产生事件，最快也要等倒计时每秒跳一次（实测 B站 空了 342ms） | 目标应用一进前台就启动**主动探测**（窗口期内周期性读界面），点击时机取决于按钮何时真的出现。B站 实测压到 **74ms** |
| 第 4 轮 | **"每次都慢一点"**：贴吧 连测时启动到点击从 2.94s 一路恶化到 5.19s，点击时倒计时 05→04→03→02→01 每次退一格 | 元凶是 10 秒的"成功冷却"挡住的其实是**下一次启动**（实测启动间隔约 12 秒时冷却仍未过期）。冷却改为跟随启动重置 + 缩短到 3 秒 |
| 第 4 轮 | 探测循环用"最后一次事件的包名"判断是否继续，被系统弹窗短暂抢走包名后循环自杀，静态广告期间再也起不来 | 改为看 `rootInActiveWindow` 的**真实包名**，并加绝对时长上限 |
| 第 4 轮 | 循环换代时，正在执行的旧循环会把自己重新排队，形成**孤儿循环**，每启动一次多一个，都在读 400 节点的界面树 | 循环开头加身份校验，发现自己已被换代就立刻退出 |
| 第 4 轮 | 贴吧 的广告在启动后 **2.4 秒**时还没出现（截图仍是 49KB 的纯色 logo，广告是 1.3MB），3 秒窗口有被"广告还没来窗口就关了"的风险 | 默认 `windowMs` 从 3000 提到 **5000** |

### 贴吧 速度的最终测量（每轮 5 次冷启动）

| | 启动→点击 | 点击时广告倒计时 | 说明 |
|---|---|---|---|
| 修复前 | 2.94 → 3.61 → 4.39 → 5.19s | 05 → 04 → 03 → 02 → 01 | 单调恶化，接近完全不动作 |
| 修复后 | 2.93 / 3.04 / 3.37 / 3.19 / 2.84s | 05 / 05 / 05 / 04 / 05 | 稳定，且都在广告上屏的第一秒内点到 |

**结论：剩下的约 3 秒不是我们的开销，而是贴吧 自己冷启动 + 加载广告的时间。**
证据是同一轮采样里，启动后 **+2.4 秒**时屏幕上还是贴吧 的纯色 logo（截图 49KB），
而广告是 1.3MB 的彩色大图。我们点击时倒计时还显示「05」，说明广告上屏不到 1 秒就被点掉了。

## 规则库

规则库是整个项目真正的长期资产：代码写一次，规则要跟着几百个 App 的版本一直维护。
所以格式刻意做成"人能看懂、能手写"。

`app/src/main/assets/rules.json`：

```json
{
  "version": 1,
  "rules": [
    {
      "pkg": "com.example.app",
      "name": "示例应用",
      "enabled": true,
      "windowMs": 3000,
      "activityHints": ["Splash", "Welcome", "AdActivity"],
      "evidence": ["countdown", "activity_hint", "fullscreen_media"],
      "strategies": [
        { "type": "node_text" },
        { "type": "tap_ratio", "x": 0.93, "y": 0.045 }
      ],
      "abortIf": [
        { "type": "has_edittext" },
        { "type": "text_contains", "value": "登录" }
      ]
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `pkg` | 必填，目标应用包名 |
| `windowMs` | 进入前台后允许介入的时间窗，省略为 3000，上限 10000 |
| `activityHints` | Activity 名关键字，命中即作为"疑似广告页"的旁证 |
| `evidence` | 允许解锁盲点策略的旁证类型，省略为全部三种 |
| `skipRegion` | 是否额外把候选限制在顶部。`full`（默认，不限位置）/ `top`（只认顶部 25%）。默认 full 是实测结论，见上文 |
| `strategies` | 按顺序尝试，命中即停。`node_text`（文本命中）/ `tap_ratio`（盲点坐标）/ `global_back`（返回键） |
| `abortIf` | 熔断条件。`has_edittext` / `text_contains` |

**解析层的兜底行为**（都有单元测试）：

- 缺 `pkg` 或缺 `strategies` → 丢弃整条规则
- 缺 `windowMs` / `evidence` → 补默认值，而不是变成 `0` / `null`
- 未知策略类型 → 只丢弃该策略，其余保留（向前兼容：新规则库不会让旧客户端崩溃）
- `x` / `y` 越界 → 夹到 `[0, 1]`

> 为什么要专门写这层：Gson 不走 Kotlin 构造函数，而是用 Unsafe 分配再反射填字段，
> **省略的字段会变成 `0`/`null` 而不是 Kotlin 默认值**。对手写维护的规则库来说，
> 那意味着"漏写 `windowMs` 规则就永远不生效，且没有任何报错"。

## 构建

在本机验证过的路径（无需安装 Android Studio）：

```powershell
powershell -File tools/setup-sdk.ps1   # 首次：引导 SDK + Gradle（约 300MB）
powershell -File build.ps1             # 单元测试 + 打 debug APK
```

标准路径（有 Android Studio / 已装 SDK 的机器）：

```bash
./gradlew :app:testDebugUnitTest
./gradlew :app:assembleDebug
```

产物：`app/build/outputs/apk/debug/app-debug.apk`

- JDK 17、AGP 8.7.3、Kotlin 2.0.21、Gradle 8.11.1
- `compileSdk 35` / `minSdk 26` / `targetSdk 35`
- 依赖只有 AndroidX、Material 和 Gson，全部为自由许可，无 Google Play Services（为 F-Droid 准备）

### 构建环境里的几个坑（都实际踩过）

| 现象 | 原因与处理 |
|---|---|
| shell 里所有 HTTPS 都失败，报 `schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS`，但 DNS、TCP 443 都正常 | Windows 的 schannel 在 TLS 握手时要往 `%APPDATA%\Microsoft\Crypto` 写密钥容器。该目录不可写时（例如进程被文件沙箱限制），HTTPS 就起不来。**不是墙**。JDK 的 JSSE 不依赖 schannel，`tools/Download.java` 就是为此写的 |
| `android sdk install` 只装上了第一个包 | 新版 Android CLI 的 `sdk install` **一次只接受一个包**，要分开调用。另外 `sdkmanager` 已被弃用，`--list` / `--licenses` 也不再需要 |
| 构建报 `Unable to initialize metrics, ensure C:\Users\...\.android is writable` | AGP 想往用户目录写统计信息。只是警告，不影响构建 |
| `gradle.bat : Couldn't open current thread, error = 5` | 沙箱下原生文件监视器不可用。已在 `gradle.properties` 里设 `org.gradle.vfs.watch=false` 关掉 |
| PowerShell 脚本里中文注释导致诡异错误（变量莫名变 null） | Windows PowerShell 5.1 读**无 BOM** 的 `.ps1` 时按 GBK 解码，UTF-8 中文字节被误解码后可能产生反引号，把下一行代码续进注释。所以 `build.ps1` / `tools/setup-sdk.ps1` **必须带 UTF-8 BOM** |
| Gradle Wrapper 首次运行很慢 | `gradle/wrapper/gradle-wrapper.properties` 里的 `distributionUrl` 可换成 `https://mirrors.cloud.tencent.com/gradle/gradle-8.11.1-bin.zip` |

## 在真机上验证（M1 验收清单）

我没法替你完成这一步——判定逻辑可以离线测试，但"能不能真的点掉广告"只有在真机上、对着真实 App 才知道。

> **用 OPPO / ColorOS 手机的话，先看 [ColorOS 使用指南](docs/usage-oppo-coloros.md)。**
> Android 13 起侧载应用的无障碍开关默认是灰的，而且 ColorOS 会自己回收无障碍权限 ——
> 这两件事不处理，装上也用不了。指南里还有一条 adb 命令可以直接绕过前者。

1. 安装 APK，打开应用
2. 点「打开无障碍设置」，找到「广告跳过」并开启
   - **Android 13+ 若开关是灰的**：`设置 → 应用 → 广告跳过 → 右上角 ⋮ → 允许受限设置`，再回来开启
   - 也可以点「复制 ADB 授权命令」，用一次 ADB 绕过（注意该命令会覆盖已有无障碍服务列表）
3. 回到应用主界面，确认状态显示"已开启"
4. 完全退出一个目标 App（从最近任务里划掉），再重新打开它
5. 回到本应用查看**调试日志**，逐条核对：
   - 有没有出现 `服务已连接`？
   - 打开目标 App 时，日志里有没有对应的判定记录？
   - 是"已点击"（成功识别）还是"在时间窗内但未找到跳过目标"（没识别到）？
   - 有没有出现 `疑似误点` 或 `已连续误点`？

### 需要回报的信息

| 现象 | 需要提供 |
|---|---|
| 完全没反应 | 日志里有没有这个包名的任何记录 |
| 没识别到 | 目标 App 名称、跳过按钮上的**完整文字**（例如"跳过 3"） |
| 点错了 | 日志中的"疑似误点"行、跳到了哪个界面 |
| 识别到但没点掉 | 日志中的"点击后「跳过」仍存在"行 |

日志本身就是 M1 交付物的一部分：没有它，"广告没跳过"这个反馈无法变成可修复的信息。

| 阶段 | 内容 |
|---|---|
| **M1**（已完成） | 无障碍服务 + 判定引擎 + 安全阀 + 真机调试面板；统计、服务心跳、支付类永不接管、应用内切换夜间模式 |

| M4 | 远程规则热更新（**必须带签名校验**，规则库投毒等于让用户手机乱点）、社区贡献流程、F-Droid 打包 |

**M1 → M2 之间的 go/no-go 判断点**：如果 10 个 App 的成功率低于 60%，或者误点率超过 5%，就该重新评估方案而不是继续堆功能。

**这个判断点已有数据（2026-10-17）**：按"**遇到广告的启动次数**"计，各应用成功率 80%~100%，**误点为 0** → 结论是**继续，进 M2** ✓
（口径说明：分母是"遇到过广告的启动次数"，不是"点击次数" —— 后者会被试探性点击的失败拖低，见 `docs/`）

## 风险与免责

- **Google Play 不允许此类用途**：Play 政策将 `AccessibilityService` 限定于辅助残障用户，
  且历史上清理过广告拦截类应用。因此本项目只通过 GitHub / F-Droid 分发。
- **存在法律风险**：绕过广告可能违反目标应用的用户协议。同类项目已有先例——
  李跳跳于 2023 年 9 月收到律师函后无限期停止更新。
  本项目定位为开源、非营利的个人工具，不提供规则库托管服务，不进行二次分发。
- **请自行评估使用风险**，尤其是涉及账号、支付的应用。
